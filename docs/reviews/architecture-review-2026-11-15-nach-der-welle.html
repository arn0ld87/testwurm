What the Windows run found

Three defects that no amount of reading would have found. They live behind cfg(target_os = "windows"), and the CI built only macOS and Linux — so the Windows binary did not compile, and nobody had noticed.

defect 1 · the service never started

sc.exe create registered the agent — with no arguments at all. Even fixed, it could not work: the agent never reports to the Service Control Manager, so the start times out with FAILED 1053. The registry entry existed and did nothing.

The way that starts is the run key: it is executed at every sign-in. install_run_key sets it, and the agent calls that instead of the service.

defect 2 · the error message was empty

sc.exe and schtasks write their failures to stdout. The module read only stderr and reported “Dienst-Fehler: ” — a failure with no text in it, which hides the cause without hiding the failure.

The message now reads both streams, and the call goes to sc.exe without a shell in between — cmd.exe /C split the line at the quotes around the display name.

defect 3 · the agent gave up on Windows

Discovery was the ARP sweep alone. It needs AF_PACKET raw sockets and exists only under Linux — so on Windows the agent logged the failure and exited with code 1. Without ARP there was no run at all.

The range is now knocked on instead: every address in --start … --end is a candidate, and the TCP scan in the propagation decides who answers. kx_scanner::ip_range supplies them, capped at 4096 addresses.

the guard that keeps it that way

A fourth CI job: cargo check --target x86_64-pc-windows-gnu. The Windows path is checked on every push now. The job needs mingw-w64 — ring ships a build script that compiles C even when nothing links.

The loop, not the session

The Windows test is a script now, not a sequence of keystrokes: kx/scripts/kx-vm-test.sh starts the agent in the VM and answers with one verdict. It is agent-runnable and deterministic — one command, one judgement.

What is still open

ISSUE-15 · the KXENC container has no cipher

The format describes header, footer, chunk numbering, AAD and nonces — and encrypts nothing. The worm transports passwords and NT hashes, not files. One correction to the first review: the module is not entirely dead. KexId is load-bearing in the live crypto path, so it has to be lifted out before the container part can go.

the task channel runs any command

It is bounded by a timeout now, but there is no whitelist: the token is full execution on the target. That is a policy decision, not a defect, and it is deliberately not taken here.

never run against a real domain

The SMB relay to DCSync was exercised only as a command line. No Windows domain controller, no real NT hashes, no relay attempt.
