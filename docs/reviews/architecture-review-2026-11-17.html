1 · Das KXENC-Containerformat hat 66 Interface-Items und null Aufrufer

Strong

Dateien: kx/crates/kx-core/src/format.rs (602 Zeilen Implementierung, 241 Zeilen Test), kx/crates/kx-core/src/kex.rs

Heute

pub const FOOTER_MAGIC, FOOTER_LEN, TAG_LEN, NONCE_LEN,
  DEK_LEN, HOST_ID_LEN, BUILD_ID_LEN, FILE_ID_LEN,
  WRAPPED_DEK_LEN, AAD_LABEL
pub enum CipherId · pub enum KexId · pub struct FooterFlags
pub struct Range · pub struct Footer · pub struct ChunkRef
pub struct ChunkContext
pub fn plan_ranges · chunks_for_ranges · chunk_iter
pub fn nonce_for · aad_for · crc32

66 öffentliche Items. Nach dem KexId-Lift ruft nichts mehr in das Modul.

Ziel

Ein Aufrufer, der eine Datei versiegeln will, muss eine Funktion kennen — nicht 66 Items, die zusammen das halbe Wire-Format beschreiben. Das Interface schrumpft auf das, was ein Aufrufer wirklich braucht; das Layout, die AAD und die Noncen liegen dahinter.

Der Löschtest: Nimmt man das Modul weg, verschwindet eine Spezifikation — es verteilt sich nicht auf Aufrufer. Es ist kein Durchreicherer, sondern eine Implementierung ohne Aufrufer.

Problem: Das größte flache Modul des Baums. Sein Interface beschreibt ein Containerformat vollständig — und die Chiffre, die hineingehört, fehlt (ISSUE-15, #31). 241 Zeilen Test prüfen Code, den niemand benutzt.

Der zweite Fund im selben Modul: format.rs:89 definiert eine eigene KexId — Werten 0 und 1, mit derselben Serde-Form wie kex.rs:15. Wer kex::KexId benutzt, benutzt eine andere Definition als das Format. Eine Änderung an einer bleibt an der anderen unbemerkt.

Lokalität: Der Wert KexId ist eine Wire-Kennung. Er steht jetzt an zwei Orten, und nur einer davon ist der benutzte. Das ist genau die Art Drift, die ADR-0001 für die Feldmengen verhindert — nur für die Kex-Art nicht.

Was tiefer ginge: ISSUE-15 umsetzen — dann bekommt das Modul seinen Aufrufer und sein Interface schrumpft auf das, was ein Aufrufer braucht. Vorher: die zweite KexId-Definition entfernen, damit der Wert wieder an einer Stelle steht. Das Modul selbst zu löschen wäre der falsche Weg: die Spezifikation ist die Grundlage von ISSUE-15.

Tests: Die 241 Testzeilen prüfen Formatlogik. Mit einem Aufrufer wandern sie hinter das Interface: ein Test über seal() prüft die Verschlüsselung, nicht die Noncen-Herleitung.

2 · Der Master-Key lebt kürzer als die Beute

Strong

Dateien: kx/crates/kx-agent/src/hostkey.rs, kx/crates/kx-agent/src/meldung.rs, kx/crates/kx-server/src/db.rs

Heute

KeySealer { server, keys: Mutex<HashMap> }

Der Memo lebt so lange wie der Prozess. Der Server überschreibt sealed_master bei jeder Registrierung.

Lauf 1 kapselt Key A → Beute mit A
Lauf 2 kapselt Key B → sealed_master = B
Die Beute aus Lauf 1 ist mit B nicht zu öffnen.

Ziel

Der Master-Key ist eine Eigenschaft des Hosts, nicht des Laufs. Er muss so lange leben wie die Beute, die er öffnet — sonst ist das, was der Server hält, teilweise tot.

Lokalität: „der Schlüssel dieses Hosts" ist eine Aussage über den Host. Heute steht sie an zwei Stellen mit zwei Lebensdauern: der Memo (Prozess) und die Datenbank (dauerhaft).

Beleg: kx-agent/src/hostkey.rs — der Memo sitzt im KeySealer, und der KeySealer wird einmal pro Prozess gebaut. kx-server/src/db.rs — sealed_master=COALESCE(NULLIF(?8,''), sealed_master): jede Registrierung mit neuem Siegel ersetzt das alte.

Fehlerpfad: Der Agent läuft im Fünf-Minuten-Takt. Der Operator holt die Beute von heute — der Chiffretext des Vorlaufs lässt sich mit dem heutigen sealed_master nicht öffnen. Kein Fehler, keine Warnung: die Zeile steht da und ist unlesbar.

Das ist eine Betreiberfrage, keine reine Codefrage: entweder der Key lebt so lange wie die Beute (deterministisch je Host abgeleitet, oder der Server behält die alten Schlüssel), oder der Operator akzeptiert, dass nur die letzte Runde lesbar ist. Erfasst als #70.

3 · Die Test-Adapter stehen im öffentlichen Interface

Worth exploring

Dateien: kx/crates/kx-exploit/src/smbrelayx.rs (Zeilen 138–168), kx/crates/kx-exploit/src/lib.rs:15

Heute

pub struct Aufzeichnung { … }
pub fn neu(ergebnis) -> Self
pub fn aufrufe(&self) -> Vec<Aufruf>

Das Modul ist pub mod smbrelayx — der Adapter ist Teil des öffentlichen Interface. Benutzt wird er nur von den eigenen Tests des Crates (Zeilen 510, 539).

Ziel

Der Seam ist das Trait Werkzeug — das bleibt öffentlich, weil es der Ort des Vertrags ist. Der zweite Adapter (die Aufzeichnung) gehört hinter den Seam: er ist ein internes Werkzeug der Prüfung.

Der Agent macht es längst vor: die Attrappe in meldung.rs:217 ist ein struct im Testmodul, nicht pub.

Problem: Das Interface trägt einen Gegenstand, den kein Aufrufer braucht. Wer kx_exploit::smbrelayx benutzt, lernt eine Klasse kennen, die nur für die eigenen Tests da ist. Das ist die Kehrseite von „zwei Adapter = echter Seam": der zweite Adapter macht den Seam real, muss aber nicht **öffentlich** sein.

Löschtest: Löscht man Aufzeichnung aus dem öffentlichen Interface, verschwindet kein Verständnis für Aufrufer — die Tests bleiben, sie finden die Attrappe nur im Testmodul statt im Interface.

4 · Ein Fehler der Beute-Extraktion erreicht die Zählung nicht

Worth exploring

Dateien: kx/crates/kx-agent/src/lauf.rs (die Sammlung der lokalen Beute)

Problem: Die Extraktoren des Systems (LSASS, Credential Manager, /etc/shadow, SSH, AWS) liefern ein Ergebnis pro Quelle. Schlägt eine Quelle fehl, wird das Ergebnis verworfen — der Lauf meldet „0 Beute" so, als wäre nichts dagewesen. Der Fehler erscheint nirgends: weder in der Zählung noch in der Zusammenfassung noch im Exit-Code.

Fehlerpfad: Auf einem Windows-Ziel ist LSASS geschützt, der Extraktor scheitert. Der Agent meldet „19 Beute gemeldet, 0 verloren" — und der Operator hält die Zielhost für vollständig ausgelesen. Die Information, was fehlt, geht verloren.

Lokalität: Die Aussage „das ist alles, was auf diesem Host lag" gehört an eine Stelle. Heute liegt sie verstreut: die Extraktoren in kx-win/kx-posix, das Wegwerfen in lauf.rs, das Zählen in meldung.rs. Erfasst als #71.

Was tiefer ginge: Die Sammlung liefert ein Ergebnis mit Zählern und den Fehlern. Der Lauf meldet beides — die Zahl und die Lücke. Der Extraktionsfehler wird dann eine eigene Größe neben „verloren", nicht ein stilles Verschwinden.

5 · Das Port-Interface trägt vier Aufrufe; der Meldeweg braucht zwei

Worth exploring

Dateien: kx/crates/kx-agent/src/c2.rs (das Trait C2Port), kx/crates/kx-agent/src/meldung.rs, kx/crates/kx-agent/src/tasks.rs

Problem: melde(port: &dyn C2Port, …) verlangt einen Port, der vier Methoden hat — genutzt werden zwei. Wer meldung.rs aufruft, muss trotzdem das ganze Interface kennen, weil der Parameter typisiert ist. Das Interface des Meldewegs ist damit breiter als sein Bedarf.

Das Gegenargument (ernst zu nehmen): Der Port ist der C2-Zugriff des Agenten. Zwei Traits an einer Stelle („Meldung" und „Tasks") zerlegen den Seam in zwei — und die Regel „ein Adapter = hypothetisch, zwei = echt" würde für beide gelten, aber die Fragmentierung kostet mehr, als sie gewinnt. Diese Karte ist deshalb Worth exploring und nicht Strong: die Richtung muss erst gegen den Zugewinn an Übersichtlichkeit abgewogen werden.

Alternative Richtung: Nicht das Trait schmaler machen, sondern die Frage enger stellen: melde könnte die Registrierung und den Upload als eine Operation anbieten („melde diesen Fund"), statt zwei Aufrufe zu koordinieren. Dann bräuchte der Aufrufer nur eine Methode, und die Reihenfolge läge tiefer im Modul.

6 · Die Zählung beschreibt den Transport, nicht den Serverzustand

Worth exploring

Dateien: kx/crates/kx-agent/src/meldung.rs (die Zähler), kx/crates/kx-agent/src/main.rs (die Zusammenfassung)

Problem: „Beute gemeldet" heißt: der Upload-Aufruf wurde mit Erfolg beantwortet. „Beute verloren" heißt: der Aufruf wurde mit einem Fehler beantwortet. Beides ist eine Aussage über die Verbindung. Was der Server daraus gemacht hat, sagt keiner.

Fehlerpfad: Der Server schreibt die Zeile, die Antwort geht auf dem Rückweg verloren (Timeout nach dem Schreiben). Der Agent zählt „1 Beute verloren", der Server hat sie. Oder umgekehrt: der Server lehnt ab, der Agent hat ein anderes Fehlerbild — der Zähler kann es nicht unterscheiden.

Warum das zählt: Der Zähler entscheidet über den Exit-Code, und der Exit-Code ist die Meldung an den Betreiber: „der Wurm lebt und hat geliefert" oder „hier ist etwas schiefgegangen". Wenn die Zahl nicht sagt, was beim Server angekommen ist, sagt sie auch nicht, was der Betreiber tun muss.

Zwei Wege: (a) Der Zähler bleibt Transportgröße, wird aber so benannt, dass niemand mehr „gemeldet" mit „angekommen" verwechselt. (b) Der Agent prüft nach dem Upload nach — beim Host-Nachschub steht, ob der Server die Zeile hat. (b) kostet einen zusätzlichen Aufruf je Fund; (a) kostet nichts und benennt die Wahrheit. Erfasst als Teil von #69.

Geprüft und in Ordnung befunden

Damit die nächste Runde diese Stellen nicht erneut vorschlägt:

  • meldung.rs — die Reihenfolge „erst Host, dann Beute" liegt im Modul und ist getestet; das Interface ist sechs Items. Tief.
  • lauf.rs — Umgebung hat zwei Adapter (System, Attrappe), der Seam ist echt. Das Interface ist klein; 312 Zeilen Implementierung dahinter. Tief.
  • c2.rs (Server) — der Router steht in der Bibliothek, das Binary startet ihn; das öffentliche Interface ist app() und AppState, die Handler sind privat. Tief.
  • dashboard.rs — die Feldlisten werden aus den FIELDS der Typen gebaut, das HTML entsteht daraus. Die Kopie ist weg. Richtig.
  • client.rs — die CSV-Spalten stehen in einer Konstante und werden gegen FIELDS geprüft; die Rechte der Exportdatei werden auch bei einer vorhandenen Datei auf 0600 gesetzt. Richtig. (Ein Schönheitsfehler bleibt: der Rechte-Block steht zweimal hintereinander — aus einer Skript-Editur. Wird mitbehoben.)
  • c2.rs (Kern) — die Feldmenge eines Wire-Typs ist eine Konstante am Typ; die Golden-JSON-Fixtures und das Key-Set-Pinning halten sie fest. Richtig.
  • hostkey.rs (Kern) — das Memo je Host ist richtig und verhindert die Doppel-Kapselung. Richtig. (Nur die Lebensdauer des Keys ist offen — Kandidat 2.)

Top-Empfehlung

Erst der Master-Key (Kandidat 2), dann das KXENC-Format (Kandidat 1)

Kandidat 2 ist die einzige Stelle, an der der Umbau dem Betreiber etwas verspricht, das er nicht halten kann: Der Server hält Beute, die sich nicht öffnen lässt. Das ist kein Architektur-Geschmack, sondern eine Aussage über die Operierbarkeit — und die Entscheidung, wie es gelöst wird (Key lebt so lange wie die Beute, oder der Operator akzeptiert nur die letzte Runde), gehört dem Betreiber, nicht dem Refactoring.

Kandidat 1 ist die größte Einzelposition im Baum und über ISSUE-15 vorbereitet: Das Format hat keinen Aufrufer und keine Chiffre — beides ist dieselbe Arbeit. Diese beiden Kandidaten hängen an derselben Frage: welche Aussagen über verschlüsselte Beute macht das System, und wo stehen sie?

Kandidaten 3 bis 6 sind Haltungsfragen: die Adapter im Interface, die verschluckten Extraktionsfehler, die Breite des Ports und die Bedeutung der Zähler. Sie lohnen sich, aber sie warten auf eine Entscheidung, die nichts blockiert.
